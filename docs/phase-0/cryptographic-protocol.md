# Cryptographic protocol version 1

Status: **draft; not approved for implementation**.

## Primitive suite

| Purpose                  | Primitive                                   |
| ------------------------ | ------------------------------------------- |
| Password KDF             | Argon2id v1.3                               |
| Key separation           | HKDF-SHA-256                                |
| Authenticated encryption | AES-256-GCM, 128-bit tag                    |
| Random bytes             | Browser cryptographic RNG                   |
| Text encoding            | UTF-8 without implicit normalization        |
| Object serialization     | Deterministic CBOR (pending final decision) |

No caller may substitute algorithms based on runtime availability. Unsupported
clients must fail with a clear compatibility error.

## Binary conventions

- Integers are unsigned, fixed-width, big-endian unless the selected standard
  mandates another encoding.
- UUIDs are encoded as their 16 raw bytes, not textual UUID strings.
- Length-prefix variable byte strings with a four-byte unsigned length where a
  container format does not already define lengths.
- Base64url without padding is used only at JSON/HTTP boundaries.
- Password bytes are `UTF8(masterPassword)` exactly. Amethyst does not silently
  trim, case-fold, or Unicode-normalize a master password.

The UI must warn if a password begins or ends with whitespace, while preserving it.

## Account KDF

Inputs:

```text
password = UTF8(masterPassword)
salt = 16 bytes generated by the browser CSPRNG
memory = pending benchmark; provisional 65536 KiB
iterations = provisional 3
parallelism = pending benchmark; provisional 1
outputLength = 32 bytes
argon2Version = 0x13
argon2Type = Argon2id
```

Output:

```text
masterRootKey = Argon2id(password, salt, parameters)
```

Parameters are stored per account and are authenticated indirectly when the key-
wrapping operation succeeds. Clients must enforce protocol-defined minimum and
maximum values before allocating memory to prevent hostile pre-login responses from
causing resource exhaustion.

## Domain-separated key derivation

Use HKDF-Extract with a 32-byte all-zero salt, then HKDF-Expand:

```text
prk = HKDF-Extract(SHA-256, zero32, masterRootKey)

keyEncryptionKey = HKDF-Expand(
  SHA-256, prk, UTF8("amethyst/v1/key-encryption"), 32
)

loginSecret = HKDF-Expand(
  SHA-256, prk, UTF8("amethyst/v1/authentication"), 32
)
```

Keys may not be derived by splitting a single byte array or by reusing labels.

## Vault-key creation and wrapping

The client generates a uniformly random 32-byte `vaultKey`. It is independent of
the master password.

```text
wrapNonce = random(12)
wrapAAD = encode(
  "amethyst-key-bundle",
  protocolVersion = 1,
  userId,
  kdfAlgorithmId,
  kdfParameters,
  kdfSalt
)

wrappedVaultKey = AES-256-GCM-Encrypt(
  keyEncryptionKey,
  wrapNonce,
  vaultKey,
  wrapAAD,
  tagLength = 128
)
```

The user ID must be allocated before wrapping. The registration protocol therefore
uses a server-issued, short-lived registration ID or a client UUID accepted as the
final user ID. This choice must be fixed before test vectors are generated.

The API stores the KDF configuration, nonce, ciphertext/tag, and format version. It
never receives `keyEncryptionKey` or `vaultKey`.

## Vault object envelope

Logical server representation:

```text
ObjectEnvelopeV1 {
  objectId: UUID
  nonce: 12 bytes
  ciphertextAndTag: bytes
  formatVersion: 1
  revision: unsigned 64-bit integer
}
```

Plaintext object representation:

```text
VaultObjectV1 {
  schemaVersion: 1
  objectId: UUID
  objectType: login | folder | settings
  createdAt: integer milliseconds since Unix epoch
  updatedAt: integer milliseconds since Unix epoch
  payload: type-specific map
}
```

The duplicated plaintext `objectId` must equal the ID bound into AAD after
decryption.

Encryption:

```text
objectNonce = random(12)
objectAAD = encode(
  "amethyst-vault-object",
  protocolVersion = 1,
  userId,
  objectId,
  formatVersion = 1
)
plaintext = deterministicEncode(VaultObjectV1)
ciphertextAndTag = AES-256-GCM-Encrypt(
  vaultKey, objectNonce, plaintext, objectAAD, 128
)
```

Revision is excluded from v1 AAD so the server may assign a new sync revision
without re-encryption. Object ID and the encrypted internal update timestamp prevent
accidental substitution but do not stop a malicious server from replaying an older,
otherwise valid object. Rollback resistance requires a client-held signed state or
transparency mechanism and is outside v1.

## Object contents

Login objects encrypt at least:

- Display name
- Username
- Password
- URI list and match rules
- Notes
- Custom fields
- Folder ID
- Favorite flag
- Entry creation/update timestamps

Folder objects encrypt their names and local metadata. Account settings that may
reveal vault behavior should also be encrypted objects.

## Decryption behavior

1. Validate envelope version, lengths, and supported algorithms.
2. Reconstruct AAD from trusted authenticated-account context and object ID.
3. Perform one authenticated decryption operation.
4. On tag failure, discard all output and return a generic corrupted-data result.
5. Decode using strict canonical rules; reject duplicate keys and unknown critical
   fields.
6. Confirm internal object ID and schema version.

No fallback algorithm, alternate AAD, password correction, or partial recovery is
permitted.

## Locking and memory lifecycle

On lock, logout, account switch, or fatal cryptographic failure, the client must:

- Release references to master root, derived keys, vault key, decrypted objects,
  search index, and generator history.
- Overwrite mutable byte buffers where the runtime permits.
- Terminate crypto workers that may retain WASM memory.
- Clear rendered secret values and pending clipboard timers.

JavaScript garbage collection prevents guarantees about immediate erasure. This is
a best-effort exposure reduction, not secure memory.

## Master-password change

1. Authenticate and re-enter the current master password.
2. Derive and unwrap the current vault key.
3. Generate a new random KDF salt and derive new keys.
4. Wrap the existing vault key with the new key-encryption key.
5. Submit the new verifier inputs and key bundle as one versioned request.
6. Server replaces them atomically and increments the account security version.
7. Revoke every session, including the initiating session.

Vault objects are not re-encrypted. A separate vault-key rotation operation, if
later added, must decrypt and re-encrypt every object and support interruption.
